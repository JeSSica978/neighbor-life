# 阶段三业务与验证记录

2026-11-24，Asia/Shanghai。当前秒杀后端完整链路已通过独立数据、真实 Kafka/MySQL/Redis/HTTP 验证。Chrome Network 与本轮 VS Code Consumer 异步断点仍为 UNKNOWN，阶段三未整体验收，不进入下一阶段。

## 当前业务规则

- 秒杀券必须 type=1、status=1 且在配置的时间窗口内。库存未初始化时拒绝预扣。
- 秒杀券一名用户对同一张券只能创建一张订单。Redis SET 资格检查、数据库秒杀唯一约束和事务幂等共同保护；同订单消息重发不会再次扣数据库库存。
- HTTP 秒杀成功表示请求已经写入 Redis 预扣及 outbox；订单落库后是状态 1（待支付），没有进行支付。
- 收藏目前只保存 localStorage，没有后端店铺收藏接口。关注用户接口不能替代店铺收藏。
- 点赞复用既有接口，MySQL 保存计数，Redis ZSET 保存用户关系。前端写请求后读取真实详情；本轮未实现点赞的跨 MySQL/Redis 事务。
- 优惠券列表 SQL 返回上架的普通券与秒杀券（type=0/1、status=1），前端分组展示。2026-11-25 更新：普通券 POST `/voucher-order/normal/{id}` 支持同一用户多次购买，每次购买一张。新购买生成新请求编号；同一 `Idempotency-Key` 重试返回原订单，取消、支付后可用新编号继续购买。数据库 `request_id` 保护请求幂等，`seckill_voucher_id` 的唯一约束只限制秒杀券；需先执行 `phase5-normal-voucher-repurchase.sql`。普通券不扣秒杀库存，不经过 Lua/Kafka；支付仍为无扣款模拟，尚无金额快照。
- 购买价与抵扣面额都以分存储，面额不是商品原价。秒杀落库后前端查询券列表刷新真实库存，当前 mode=mysql。退出浏览器不撤销服务端 token，后端登出仍未实现。

## 秒杀恢复边界

Lua 同时预扣、写资格、reservation 和待投递 Stream；后台等待 Kafka ack 后删除 outbox；Consumer 经 Spring 事务代理扣 MySQL 库存和插入订单，返回后完成 Redis 状态，最后容器确认 offset。发送超时不能直接加回库存，需以原订单 ID 重试。

本地 Redis AOF/appendfsync=always、订单 Topic retention.ms/bytes=-1。基础设施可恢复且初始库存一致时，已验证故障恢复后的库存一致。单节点磁盘永久丢失、外部修改库存、永久业务冲突仍需人工冻结该券、对账和恢复；不是已实现的分布式事务。Consumer 永久错误会保留消息并阻塞分区，不能靠跳过 offset 冒充修复。

## 验证与数据

实际通过：登录、店铺查询、点赞持久化、Lua 0/1/2/3/4、Kafka 投递/消费、MySQL 事务及幂等、重复请求、售罄、重复消息、Consumer 恢复、INSERT 失败回滚/重试、Producer 不可达重试、3 用户竞争 2 份库存。

本轮初始原数据为 14 店铺、5 用户、4 笔记、1 普通券，0 秒杀券/订单。只创建和清理独立 fixture；清理后行数及默认链路原数据 SHA256 恢复。没有重建数据库、清空 Redis、回退共享 ID 序列，未提交/Push。
