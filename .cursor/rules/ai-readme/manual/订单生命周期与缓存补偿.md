# 订单生命周期与缓存删除补偿

2026-11-24，依据当前实现和独立集成测试维护。

- 新功能需要显式执行 phase4-order-lifecycle-and-reliable-events.sql，再重启核验结构。没有迁移时功能停用并给出明确提示，不自动 DDL。
- 订单 1 待支付、2 已支付、4 已取消。模拟支付 pay_type=0，不扣款，没有第三方支付/退款。支付和取消都通过 status=1 条件更新裁决，取消是终态。
- 默认 15 分钟期限、每分钟最多扫描 100 单，每单独立事务。数据库判定有效期；查询订单有被动关单。激活会影响既有超时未支付订单，须先确定历史数据处理范围。本轮没有触碰体验店 18 / 券 26、27、28。
- 秒杀关单状态、MySQL 库存+1、持久事件同一事务。失败一起回滚。普通券没有库存模型，不伪造普通券返库存。
- 保留一人一券唯一约束和 Redis 资格 SET；取消后不能重新购买同一券。不要 SREM 用户后导致数据库唯一冲突。
- Redis 返库存 Lua 以 order:stock-restored:{orderId} 作为永久幂等标记；不自行过期。只有已取消且有持久事件的订单能恢复库存，缺失/错误库存 Key 要先核对修复，不能直接补一个初始值。
- tb_reliable_event：0待投递、1已投递、2完成、3阻塞。发送失败持久重试；Consumer 默认 8 次失败后持久阻塞再确认 Kafka 消息，日志告警；修复后明确重投。未知消息拒绝跳过。
- 缓存更新与事件同事务，afterCommit 在新事务中 DEL 并标记完成；失败由独立 Kafka Topic/Group 消费。事件 DONE 重复处理不能再次删重建的缓存。TTL 30 分钟兜底，不是强一致。
- Kafka offset 在消费者处理事务提交后确认；永久故障不能当作成功。库存恢复成功后 DB 完成标记失败，重试 Lua 应返回已处理而不再 INCR。
- 店铺编辑默认关闭，必须登录且服务端 demo 店铺白名单。没有生产商家角色模型。
- 订单金额展示目前来自优惠券，没有支付金额快照；真正支付网关、退款、核销及订单价格快照仍未实现。
- 调度线程池 4 个线程，Consumer 另有线程。断点暂停不是性能测试。
- 新关单一致性应统计占用库存的非取消订单，不能使用 stock + 所有历史订单数。旧 loadtest Fixture/Observer 需适配取消和事件清理后才能验收该压测场景。
