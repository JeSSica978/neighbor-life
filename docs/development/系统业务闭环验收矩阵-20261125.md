## 3. 故障与恢复验收

| 编号 | 注入/竞争 | 必须满足的恢复证据 |
| --- | --- | --- |
| F01 | Lua 执行前 Redis 故障或键类型异常 | 不出现部分业务成功；无不可解释库存扣减；页面重试使用原购买请求 |
| F02 | Lua 成功后 Kafka 不可用/Producer 超时 | outbox 保留原订单；恢复后同 ID 落库一次；不能靠盲目返库解决 |
| F03 | Consumer 的 INSERT/事务提交失败 | DB 库存和订单事务一起回滚；offset 不提前确认；恢复后一次提交 |
| F04 | DB 提交后 Redis 状态标记失败 | 重复消费先认原订单，DB 不再扣库；状态标记恢复后确认 offset |
| F05 | DB 已返库，Redis 补偿失败/重复恢复消息 | DB 与释放事件同事务；Redis 每个释放事件只应用一次；最终可对账 |
| F06 | 模拟支付成功通知重复、乱序、延迟或业务处理失败 | 通知持久记录、绑定校验、最终只结算一次；已关闭晚到成功有退款证据 |
| F07 | 支付/发券事务 INSERT 失败 | 不出现已支付无券且无恢复记录；通知可幂等重试；恢复后来源订单唯一 |
| F08 | 退款结果失败/成功通知重复/重启 | 券冻结/失效状态明确；退款不超实付；库存不重复释放；结果可查询 |
| F09 | 核销/退款并发和事务回滚 | 只有合法胜者；订单、券与对应流水同事务；不出现已用券被自助退款 |
| F10 | 店铺/券更新时缓存删除、旧值回填或实例故障 | 持久失效意图可重试，版本/TTL 有界收敛；所有实例最终读到新值 |
| F11 | 点赞/关注/发布后的 Redis 写失败 | DB 有权威关系/事件；重新构建后计数与动态正确，无不可解释成功丢失 |
| F12 | 过量请求和同毫秒限流请求 | 唯一计数准确，真实用户/IP维度按配置；HTTP429 与业务拒绝、系统失败可区分 |
| F13 | 生命周期启用/重启与历史数据 | 历史订单及体验数据保持原状；只有显式管理范围的新订单被处理 |

这些场景只在独立环境和专有数据上执行。故障恢复完成后，记录请求编号、订单/支付/券/退款/核销编号、库存账、可靠事件、Kafka offset 和必要日志；截图用于证明页面行为，不能代替持久化断言。

## 4. 压测准入与指标

开始压测前，主业务及权限用例、与本次实现有关的故障用例必须通过；遗留未覆盖用例须注明影响，不能把查询 HTTP200 当作交易闭环通过。

| 测试组 | 指标 | 核验方式 |
| --- | --- | --- |
| 店铺/券查询 | QPS、P95/P99、命中率、DB/Redis负载 | 固定条件、冷热缓存分开、真实业务 success |
| 普通券购买 | 新单成功率、请求重试幂等、建单吞吐 | 请求编号与不同订单对应、无秒杀资格误用 |
| 秒杀受理 | 有效受理率、库存不足/限购/429 比例 | Lua 有效预占数，不当作已落库成功数 |
| 异步落库 | 最终成功率、端到端建单延迟、lag/积压/恢复时间 | 受理 ID 对应唯一 DB 订单；在途和阻塞单解释完整 |
| 支付/发券 | 支付完成吞吐、失败/延迟通知恢复、重复结算率 | 支付单与订单与券来源一一对应 |
| 退款/核销 | 吞吐、竞争结果、重复成功数 | 退款金额上限、券状态、唯一核销与单次库存释放 |
| 稳态对账 | 库存差额、残留事件/预占、offset | 无在途时账一致；有在途时差额可由具体记录解释 |

现有 `tools/loadtest/fixture/LoadtestFixture.java`、`observer/LoadtestObserver.java`、`jmeter/seckill-async.jmx` 主要针对秒杀下单；新闭环需要增量适配。清理前先确认 offset 和在途记录，清理范围仅限本次专有数据，历史开发订单与非本轮数据保留。

验收完成后另写真实结果报告，标明环境、并发、持续时间、数据量、缓存模式、限流配置、业务成功定义和资源限制；不得用参考 PDF 中的数字补空白。
