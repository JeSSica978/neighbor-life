### 容量与可靠性边界

- 单实例 Publisher 的真实参数名是 `hmdp.seckill.publish-delay-ms`，默认 fixedDelay=1000ms；每轮读取最多 20 条，逐条等待 `.get(10s)`。持续饱和且每批读满时，理论长期投递速率低于 20 条/秒（还要加每批发送耗时）。这限制投递/最终完成能力，不等于 HTTP 准入速率上限，也不是多实例聚合吞吐的上限。
- 锁名固定为 `lock:seckill:outbox`，不包含自定义 outbox 名。共享 Redis 的多个独立 Topic/outbox 进程仍竞争该锁；只改 Topic/消费组不足以得到完全独立的性能环境。
- Topic 定义是 1 分区、1 副本；监听器未配置额外 concurrency。当前单分区消费，单券 MySQL 行锁还会串行化库存变更。增加消费者数量不会自动提高这张券的并行写入能力。
- Consumer 失败无限重试，保留消息但可能阻塞整个分区；没有已实现的最终死信修复/外部告警流程。Publisher 也没有最大重试次数，错误记录可能阻塞后续待投递消息。
- Redis 库存/资格没有自动活动结束清理；成功 reservation 设置 7 天 TTL，未完成 reservation/outbox 不自动过期。订单 Topic retention.ms/bytes=-1，未来测试消息必须有归属清理方案。

DEL 抛异常时当前 MySQL 事务通常回滚，不是“先提交 MySQL，再通过 Kafka 补偿”。DEL 在提交前会打开竞态：另一个读请求在事务未提交时读到旧数据并重新填缓存，随后事务提交，旧缓存可能继续存在 30 分钟。也未检查 updateById 的返回值。

最小补充方向：核验写成功，明确提交后失效策略；若要求可靠补偿，用和 MySQL 更新同事务持久化的删除事件，再由独立投递/消费链路幂等 DEL、记录重试/最终失败并告警；仅 afterCommit 直接发送仍有丢事件窗口。还需处理旧读回填竞态（版本校验或可靠延后再删除等方案），TTL 只是最后兜底。本轮不开发。

## 8. Redis 滑动窗口限流

源码：[RateLimiter 注解](D:/Development/neighbor-life/src/main/java/com/hmdp/limiter/annotation/RateLimiter.java)、[RateLimiterAspect.doBefore:47](D:/Development/neighbor-life/src/main/java/com/hmdp/limiter/aop/RateLimiterAspect.java:47)、[limiter.lua](D:/Development/neighbor-life/src/main/resources/limiter.lua)。ZSet 记录请求，Lua 清理窗口外成员、ZCARD 判断、ZADD 允许请求并 EXPIRE。

| 维度/接口 | 当前状态 |
| --- | --- |
| METHOD，全局到方法 | 仅 [ShopController.queryShopByType:72](D:/Development/neighbor-life/src/main/java/com/hmdp/controller/ShopController.java:72) 应用；GET `/shop/of/type`，5 秒最多 5 次。参数 typeId/current/size、用户和 IP 变化仍共用同一方法 key；不是所有接口共用的全系统总限流 |
| USER | enum 分支存在，但 getCurrentUserId 固定返回 anonymous，未读取 UserHolder；未应用到 Controller，不能称真实用户限流 |
| IP | 分支存在，但未应用到 Controller；直接信任请求头，未限制可信代理、未解析 X-Forwarded-For 链，真实 IP 正确性 UNKNOWN |
| 秒杀/普通下单 | VoucherOrderController 没有 @RateLimiter；当前不受该注解限制。`coupon:seckill:` 只是分类接口的 key 前缀，不表示秒杀已限流 |
| 响应 | RateLimitException 被 WebExceptionAdvice 包装为 HTTP 200、success=false；没有 HTTP 429 专用处理 |

当前分类完整 key 为 `coupon:seckill:com.hmdp.controller.ShopController:queryShopByType`。

**明确计数缺陷（静态审计结论，未执行 Lua）：**脚本每次 `math.randomseed(now)`，然后用 `now .. '-' .. math.random(...)` 作成员。同一毫秒的相同种子得到相同首个随机数，ZADD 覆盖已有成员，不增加 ZCARD。在当前 limit=5 时，同毫秒大量请求可能都被放行，无法保证每窗最多 5 次。该问题必须先修复并复现验证，不能直接压测后把超阈值吞吐当作限流性能提升。

其他边界：now 来自应用机器时钟，多实例时钟偏差会影响窗口；参数只检查可转数字，没有完整正值约束；返回 null 时切面放行；允许/拒绝均有日志成本。Lua 实际移除包含 `now-window` 的分数边界，统计应按 `(now-window, now]` 窗口，而非照搬注释的半开区间。注解 window 是整数秒。

最小待办：唯一请求成员、可信时间与边界测试；USER 接实际身份；IP 接可信代理策略；明确 Redis 故障时的放行/拒绝政策和 429/业务错误响应。现有五次阈值 METHOD 可先在独立环境做缺陷复现，但不能标记三维限流验收通过。

### Kafka 积压与最终落库延迟

- 监测专用 outbox XLEN、最早 Stream ID 的等待年龄、Publisher 错误和 Kafka 发送/消费速率。不能只看 Kafka lag：消息可能还没离开 Redis。
- 用 Kafka `kafka-consumer-groups.sh --describe` 对实际测试 group 查看每分区 CURRENT-OFFSET、LOG-END-OFFSET、LAG。消费提交 lag=0 也不代表所有 HTTP 已受理订单都落库，要和 outbox 与返回 ID 集合核对。
- JMeter 记录 `t_start`、HTTP elapsed/end、业务 success 和完整字符串 orderId。HTTP success=true 表示受理，需单独统计 SQL 完成数。
- 当前没有专用 commit 时间指标。数据库 `create_time` 是 INSERT 时间、默认时间精度也不适合精确毫秒提交延迟；订单 ID 的时间部分不能充当 commit 时间。
- 可用每 250ms 的外部只读批量观察器按订单主键集合读取新测试订单，记录首次可见时刻：`first_seen-t_start` 为完成延迟上界，包含采样误差；同步与异步用同样观察器/周期。先确认索引和观察开销，不高频全表扫描。
- `SECKILL_CONSUMED` 在事务和 Redis 更新后打印，可统计“消费完成”延迟，不等于精确 MySQL commit 时刻。精确提交延迟需要以后补观测，当前 UNKNOWN。HTTP per-order 轮询仅做小比例抽样，不把几千笔 100ms 轮询混入订单负载。

| 指标 | 放行/拒绝次数和比例、任意 5000ms 窗口放行数、限流错误语义、放行/拒绝 p95/p99、Redis ZCARD/TTL、Lua 耗时与 CPU；请求响应按 success/errorMsg 分类，不认 HTTP 200 为放行 |
| 一致性 | 对真实到达/放行时间按 `(t-5000,t]` 验证最多 5 次；并发放行不能重复成员覆盖。拒绝不进入业务查询；到期允许恢复。USER/IP 维度必须各自证明隔离，当前不可标通过 |
| 清理 | 读接口测量不产生订单；等待自有 key TTL 到期，或仅删除隔离环境中明确自有 key；清理新增店铺/用户。默认运行环境的全局方法 key 保留 |

当前秒杀无限流注解，A 不会自然触发 5/5s；C 测的是分类方法限流。若以后给秒杀加注解，应分别报告开启/关闭限流的独立实验，不把限流拒绝造成的轻负载当作秒杀处理能力。

当前运行的项目 Java PID 25052 未带 JDWP、未显式 -Xmx，默认业务 Topic；本轮没有重启它。真实 JVM 堆、Tomcat/Hikari 池实值未采集，标 UNKNOWN；Lettuce YAML max-active=10。不要按未采集的默认值填写压测结果。

只读消息快照：默认订单 Topic 1 分区/1 副本、retention.ms/bytes=-1；默认 group `your-group-id` offset=7、log-end=7、lag=0，outbox XLEN=0；Redis appendonly=yes、appendfsync=always。没有重置任何 offset。空闲无积压不能证明高负载排空能力。

主要风险及停止条件（未来执行前固定）：

- JMeter、Java、数据库及中间件同机抢 CPU/内存；当前空闲内存有限，先低梯度，不能直接套用千线程。固定双方资源，必要时用另一台注入机；当前端口只绑定 loopback，对外访问另需规划，不能擅自开放。
- Redis AOF always、Kafka 每条发送等待和 RECORD 同步提交、MySQL 券行锁决定实际瓶颈。不能只看 HTTP 快而忽略数千条待投递消息。
- SQL DEBUG 与限流 INFO/拒绝堆栈会产生大量 I/O；mysql 模式的日志量可能显著高于缓存命中模式。若未来决定安静性能配置，应双方统一、单独记录，保留功能验收的 DEBUG；本轮没有关闭日志或启动图案。
- 若库存不变量失效、发现无法解释的订单丢失/重复，立即停止；若 lag/outbox 持续增长且 180 秒不能排空，停止升档并保留证据。基础设施非预期错误持续超过 1%、CPU 连续 30 秒超过 85%、主机空闲内存低于 2GB 或明显持续换页时停止；阈值可在正式执行前调整但不能事后改口径。
- Topic 无限保留和 reservation/资格数据会增长；需预先预算磁盘/Redis 内存，测试尾部先排空再清理自有数据，不能 flush Redis 或 rebuild 数据库。
