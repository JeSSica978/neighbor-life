# NeighborLife 阶段三秒杀断点调试

源码日期：2026-11-24，项目 `D:\Development\neighbor-life`。

本轮真实 HTTP、Redis、Kafka、MySQL 测试通过；以下是依据保存源码编写的可执行教程。**VS Code Consumer 异步断点尚未在本轮实际操作，IDE_DEBUG_PASS=UNKNOWN。** 阶段二的店铺断点验证不能代替秒杀 Consumer 断点。

## 1. 准备独立数据

1. 若普通后端在运行，执行已有 **NeighborLife: Stop Backend** 任务。
2. 在 VS Code 保存所有源码，选择 **NeighborLife: Java Debug (JDK 11)**，暂时禁用业务断点。
3. 按 F5，等待 8081 监听、日志出现 `seckill-voucher-order-0` 的 partition assignment。
4. 在项目 PowerShell 终端执行：

```powershell
Set-Location D:\Development\neighbor-life
.\tools\Invoke-Phase3Verification.ps1 -Action Prepare
.\tools\Invoke-Phase3Verification.ps1 -Action Inspect
```

Prepare 通过真实验证码、登录、店铺、笔记、新增秒杀券接口创建独立数据；输出本轮新店铺名、手机号、用户 ID、店铺 ID、笔记 ID、三张券 ID，各库存为 3。它不会发送真实短信或支付。临时 token 只记录在 `target/phase3-fixture-private.json`，不要公开或提交该文件。已有 fixture 时会拒绝再次覆盖。


## 3. 触发请求并单步

建议每次只启用当前要检查的断点，避免长时间阻塞 Kafka 事务或前端超时。

```powershell
.\tools\Invoke-Phase3Verification.ps1 -Action Submit -VoucherIndex 0
```

这个命令使用自有测试用户的真实 token，POST 到 Prepare 输出的第一张券，HTTP 等待上限 60 秒。它不是假响应，也不会调用支付。断点中先观察 HTTP Service 的 Lua 返回值，按 F5 继续 HTTP 请求；订单 ID 表示已受理。

Publisher 在定时线程读取 Lua 写入的 outbox。Call Stack 中选择 `scheduling-1`，检查 JSON 和真实 Kafka ack 的 partition/offset，再按 F5。

Consumer 在独立 Kafka 线程执行，HTTP Controller 的 F11 不会跨线程进入它。必须在 `processMessage` 单独设置断点，从 Call Stack 中选择 `seckillVoucherOrders-0-C-1`。继续进入事务方法，看库存更新和订单插入，再回到 Consumer。最后恢复 listener，使容器能够确认 offset。

库存更新/订单插入断点中，事务尚未提交，从另一个连接查询可能暂时看不到新数据。只有事务代理返回后再做最终核验。

## 4. 核验结果与复位

禁用断点并恢复所有暂停的线程后执行：

```powershell
.\tools\Invoke-Phase3Verification.ps1 -Action Inspect
```

第一张券预期 Redis=2、MySQL=2、orders=1，其他券仍为 3/3/0。日志应按同一个订单 ID 对齐：

```text
SECKILL_LUA ... result=0
SECKILL_KAFKA_SENT ... topic=seckill-voucher-order partition=0 offset=...
SECKILL_DB_INSERT ...
SECKILL_CONSUMED ... transactionCommitted=true thread=seckillVoucherOrders-0-C-1
```

`SECKILL_DB_INSERT` 位于事务内，不能单独当作提交成功；以 Consumer 的提交后日志、数据库读回和 offset 为准。

重新测试同一批券前：

```powershell
.\tools\Invoke-Phase3Verification.ps1 -Action Reset
```

Reset 先确认真实 Kafka offset 已提交、没有自有 outbox 在途记录、库存一致且库存+订单数=3，然后只删除自有订单/资格，恢复自有券库存为 3。状态尚未完成时会拒绝复位，先恢复线程或修复投递/消费故障。该命令不会重置业务 Consumer Group offset。Kafka 只在候选前缀全部确认为自有测试消息时清理该前缀，任何原记录都会保留。

全部检查完毕：

```powershell
.\tools\Invoke-Phase3Verification.ps1 -Action Cleanup
```

Cleanup 删除自己的用户、店铺、笔记、券、订单及 Redis keys，并比较原业务表 SHA256。然后按 Shift+F5 停止 Java Debug，中间件持久卷保留。

首页 `api()` 超时为 12 秒，HTTP 断点停留更久会取消页面请求。先验证页面时禁用断点；调试时使用 60 秒等待的独立 Submit 命令。超时不会自动恢复已取消的页面请求，需要重新发起请求并用日志/Inspect 确认是否已经受理，避免把浏览器超时误判为订单丢失。
