## 1. 参考方案与实际选择

参考用户提供的《面试-黑马点评》PDF 第 32 页、第 40–53 页：单体项目采用 Spring Task 扫描；支付与关单以 `WHERE status=未支付` 的条件更新竞争；更新数据库后删除缓存，删除失败用 MQ 重试，TTL 兜底。

本项目采用状态条件更新的乐观锁思想，不增加 `version` 字段。增加 `(status,create_time)` 索引，每轮最多处理 100 单，每单通过独立 Spring 事务代理执行。默认支付期限 900 秒，扫描间隔 60 秒；订单查询补充被动关单。

PDF 示例只在业务方法中直接发送消息，未完整解决 DB 提交与 MQ 投递之间的故障窗口；某示例 Consumer 捕获异常而不抛出，也不能据此认为自动重试有效。本次在业务事务中增加 `tb_reliable_event` 持久意图，提交后处理或异步投递。只验证模拟支付，未开发第三方支付、退款或真实扣款，不照搬 PDF 的性能数字。

## 2. 订单完整链路

```text
秒杀受理 → 原 Redis Lua / Stream → 原 Kafka Consumer → MySQL 待支付订单
                                                        ↓
                               我的订单 → 模拟支付 / 取消 / 超时扫描
                                                        ↓
                           status=1 条件更新：1→2 或 1→4，只能一次成功
                                                        ↓
                       关单成功：同一事务 MySQL stock+1 + 持久返库存事件
                                                        ↓
                            独立 Kafka Topic → Lua 幂等 Redis stock+1
```

支付接口同时要求未超过数据库判定的期限。支付先成功，关单影响行数为 0，不返库存；关单先成功，模拟支付被拒绝。重复支付返回已有已支付结果；重复取消返回已取消结果。真实第三方回调若发生“关单后收款”需要另外实现退款补偿，本轮没有声称实现。

关单 MySQL 库存更新、订单状态更新、事件插入属于同一个事务。事件插入失败会一起回滚。Redis 恢复按订单 ID 使用永久幂等标记 `order:stock-restored:{orderId}`，重复处理返回 0，不重复加库存。库存 Key 缺失、类型错误或 reservation 身份冲突时拒绝执行，记录待修复事件，不能凭空新建库存。

保留数据库 `(user_id,voucher_id)` 唯一约束及 Redis 购买资格 SET。取消后仍一人一券，不释放再次购买资格；避免 Redis 允许重买、MySQL 唯一约束却拒绝插入。普通券没有独立库存模型，取消只改订单状态。

原订单消息在取消之后重发，会命中已有订单，不再扣 MySQL 库存；Consumer 的 reservation 更新只允许 `PENDING→CREATED`，不覆盖 `CANCELLED`。

## 3. 缓存删除补偿完整链路

```text
PUT /shop
  → 同事务：更新 tb_shop + INSERT tb_reliable_event
  → commit
  → afterCommit / REQUIRES_NEW：DEL cache:shop:{id} + 标记 DONE
  → 删除失败：保留 PENDING
  → Publisher：Kafka ack 后标记 SENT
  → 独立缓存 Consumer：DEL 成功 + 事件 DONE 提交后返回
  → Kafka RECORD 确认 offset
```

数据库事务回滚时不删除缓存，也不遗留事件。提交后的立即删除即使失败，业务更新已成功，前端查询事件状态，不能把“店铺保存成功”等同于“缓存已刷新”。缓存 Key 已不存在属于删除成功。

补偿 Topic 为 `shop-cache-delete`，返库存 Topic 为 `order-stock-restore`；均一分区、一副本、无限保留，使用 String 序列化。消息 value 仅为 UUID，真实业务类型及资源 ID 从 MySQL 事件读取，Consumer 不接受任意 Redis Key。与原秒杀 Topic/Group 分离。loadtest profile 的 Topic/Group 均含独立 Run ID。

事件状态：0=PENDING、1=SENT、2=DONE、3=BLOCKED。发送失败持久保留，数据库时间安排下次投递，间隔逐步增加至 30 秒；SENT 超过 60 秒仍未完成也会重新投递。Consumer 默认最多 8 次失败，测试设为 3；达到上限后先持久保存 BLOCKED，再允许该记录确认，不静默丢弃。没有事件记录或类型不匹配的未知消息继续阻塞分区，不能跳过 offset。

达到上限产生 `RELIABLE_EVENT_BLOCKED` ERROR，定时输出阻塞数量；这是日志告警，尚未对接外部告警平台。修复原因后重新投递。DONE 重复消息直接返回，不删掉之后重建的新缓存。`sent()` 的条件更新不能覆盖快速 Consumer 已完成的 DONE。

店铺真实缓存 TTL 30 分钟，空值 TTL 2 分钟。该方案是最终一致性：提交至删除完成存在短暂窗口，读取旧数据并迟到回填缓存仍可能发生，TTL 是兜底，不是强一致保证。返库存后失效当前实例的优惠券 Caffeine 及 Redis 列表；其他实例 L1 仍按既有刷新/过期策略收敛，未新增跨实例广播。

F5 开启调试，Consumer 是独立线程，需另设断点；在断点暂停时后台轮询、超时与 Kafka consumer poll 可能受影响，不能据此评估性能。直接运行用 VS Code Ctrl+F5 或既有启动方式。迁移启用后登录→店铺买券→我的订单→模拟支付/取消；白名单店铺详情中可编辑资料查看缓存状态。

本轮未执行 JMeter。新增模块优先做支付/取消竞态与故障恢复功能验证，再做有界并发测试；不把 20 轮竞态当性能结果。现有压测 Observer/Fixture 的库存公式、CANCELLED reservation 判定及事件/幂等标记清理尚需随生命周期更新，不能直接用旧一致性公式验收关单场景。已有查询/异步秒杀性能数字属于之前版本，需要固定本次源码后再测。
