# 普通优惠券购买与库存展示验证

2026-11-24，项目 `D:\Development\neighbor-life`。普通券已具备真实购买按钮和 MySQL 待支付订单接口，没有接入真实支付。

## 本次修复

| 操作 | 前端 | HTTP | 后端及结果 |
| --- | --- | --- | --- |
| 普通券购买 | `voucherElement → submitNormalVoucher → submitVoucherOrder` | POST `/voucher-order/normal/{id}` | `VoucherOrderController.purchaseNormalVoucher → VoucherOrderServiceImpl.purchaseNormalVoucher → VoucherMapper.selectForUpdate → VoucherOrderMapper.insert`，提交 MySQL 事务后返回字符串订单 ID |
| 查看自己的订单 | `submitVoucherOrder` | GET `/voucher-order/{id}` | 复用既有查询；返回真实 `CREATED` 和 status=1（待支付），其他用户无权查看 |
| 秒杀库存刷新 | `submitSeckill → submitVoucherOrder → refreshVoucherStock` | 订单落库后 GET `/voucher/list/{shopId}` | 当前配置 `hmdp.cache.voucher-list.mode=mysql`，显示最新 MySQL 库存；查询失败提示重新打开店铺，不做前端假扣减 |

普通券校验登录、有效 ID、type=0、status=1 和正数金额。复用现有 `(user_id,voucher_id)` 唯一约束，用券行锁保护并发重试；同一用户、同一券重复提交返回已有订单 ID，不新增订单。页面说明“每人限购一张”，提交后按钮显示“已下单”。普通券没有秒杀库存字段，也没有借用 Lua/Kafka 扣库存；订单 ID 仍使用现有 RedisIdWorker。不能把创建订单理解为已经付款或可核销。

既有 `WebExceptionAdvice` 将服务器异常转换为 HTTP 200、`success=false`；前端检查 success，不用 HTTP 200 判断业务成功。`NORMAL_ORDER_INSERT` 日志发生在事务内，验证还读取了提交后的订单。

## 实测

- Maven 单独选择 `Phase3IntegrationTest#verifyNormalVoucherOrders`，1 个测试、0 失败、0 错误，BUILD SUCCESS。未运行历史全量测试或压测。
- 匿名购买 HTTP 401；无效 ID、缺失券、秒杀券走普通接口、下架普通券、零金额均被拒绝。
- 真实订单 status=1、pay_time=NULL；订单 ID 作为字符串返回；重复请求返回同一 ID；其他用户查询被拒绝。
- 第二个独立用户的 8 个并发重复请求只创建一笔订单。两个不同用户可各买一张。
- 用仅命中特定新券的临时 MySQL INSERT 触发器模拟故障：返回 `success=false`、订单数为 0；删除该触发器后重试成功。秒杀库存和 outbox 没有被普通购买修改。
- 内置浏览器在独立店铺 22 上完成正常登录，购买券 45/46。MySQL 各有 1 笔待支付订单，页面都显示“已下单 / 订单已创建，待支付”。
- 同页购买秒杀券 42：Lua result=0，Kafka partition=0/offset=0，Consumer 日志 `transactionCommitted=true`；页面和 Redis/MySQL 库存均从 3 变为 2，订单数从 0 变为 1。
- 360 宽视口检查：页面 clientWidth/scrollWidth 都为 345，弹窗都为 292，没有横向溢出；控制台错误为空，临时视口恢复。
- 独立 fixture Reset 后，普通订单为 0、三张秒杀券 Redis/MySQL 库存都恢复 3；Cleanup 后原六张业务表 SHA256 指纹一致。当前店铺 18 的六笔旧秒杀订单保留。

## 使用

先停止原终端的服务，再在项目根目录普通启动：

```powershell
.\tools\Invoke-NeighborLife.ps1 -Action Run
```

打开 `http://localhost:8081/?shop=18` 并刷新。普通券 29/30 分别是付 88 抵 100 元、付 168 抵 200 元，均有“立即购买”。不用压测就能手动验证。F5 是调试运行；Ctrl+Shift+B 或上述 Run 命令是普通运行。

普通购买断点：Controller 的 `purchaseNormalVoucher`、Service 同名方法、`voucherMapper.selectForUpdate`、`query().eq(...).one()`、`save(order)`。观察 voucher.type/status/payValue/actualValue、userId、existing、order.id/status、返回的 Result；这些发生在 `http-nio-8081-exec-*` 请求线程。事务提交发生在 Service 代理返回到 Controller 前；用 GET 订单和 MySQL 查询确认提交。

证据目录：`docs/development/evidence/ordinary-vouchers/`，包括 integration-tests.json、browser-orders.json、ui-inventory-before-reset.json、ui-fixture-reset.txt、runtime-chain.txt 和截图。独立清理证明：`docs/development/evidence/phase3/fixture-cleanup-PHASE3_TEST_1795506173537.json`。证据中的店铺 22、券 42–46 已清理，不能再用这些 ID 体验。
