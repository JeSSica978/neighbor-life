# 邻享生活简历改写与面试依据

依据 2026-11-24 当前源码、阶段三功能证据与本轮实际 JMeter 结果编写。只写已验证的能力，不将学习方案或 PDF 示例数字写成自己的成绩。

## 可直接使用的版本

**邻享生活｜后端开发与优化**

**项目简介：**基于本地生活服务场景，提供商家检索、探店笔记互动、普通优惠券购买和限时秒杀功能；负责前后端联调、秒杀异步链路修复与性能验证。

**技术栈：**Java、Spring Boot、MySQL、Redis、Lua、Kafka、Caffeine、MyBatis-Plus、Docker、JMeter。

- **秒杀资格与防超卖：**使用 Redis 库存、购券用户集合和 Lua 实现原子预扣与一人一单，并在同次 Lua 执行中写入订单预留记录及 Stream Outbox；独立验证 400 用户竞争 50 份库存，创建 50 单、拒绝 350 次售罄请求，Redis/MySQL 库存一致。
- **异步订单可靠性：**恢复 Kafka 订单发送、消费与 MySQL 事务链路，以持久化 Outbox 支持发送重试，事务提交后确认消费；结合订单主键、用户券唯一约束和重复检查，验证重复请求、重复消息不会重复建单或扣库存。
- **热点查询优化：**实现优惠券列表 MySQL、Redis、Caffeine＋Redis 三模式查询，并完成同数据、同日志、50 线程的两轮 JMeter 对比；本机平均吞吐约 3967→7355→17031 req/s，二级缓存为 MySQL 的 4.29 倍，平均延迟 11.62→2.40 ms。
- **缓存与性能验证：**验证店铺空值缓存减少不存在 ID 的数据库回源；区分秒杀 HTTP 受理和最终落库指标，通过 JTL、SQL Observer、Outbox/Kafka Lag 定位批量发布瓶颈，记录库存、订单与消费 offset，并用独立 Fixture 完成测试数据清理。

## 面试时如何讲成自己的经历

以“我检查了什么、遇到什么、怎样修复或验证、还有什么边界”组织。可以这样讲：

> 我在联调时发现秒杀入口能返回订单 ID，但业务 Consumer 没有生效，所以先把受理和最终订单区分开，逐段核对 Lua、消息格式、Consumer 注册及事务提交。当前 Lua 将库存预扣和 Outbox 写入放在同一次执行，发布器收到 Kafka 确认后才删除 Outbox；消费者通过事务代理创建订单，重复消息在扣库存之前识别。随后使用独立用户和券测试重复请求、消息重放及售罄，验证库存和订单数量。
>
> 压测时没有只看 HTTP QPS。我在 40 请求/秒的短时测试中发现 HTTP 平均约 17 ms，但受理到数据库首次可见的平均延迟达到约 6.1 秒、P95 约 11 秒，主要是 Outbox 每批最多 20 条、发送后再等 1 秒造成积压。因此我目前能说明异步受理和可靠重试的实现，也能说明下一步要优化发布阶段，不能声称系统已经具备很高的完成吞吐。
>
> 查询部分使用同一店铺、同样 5 张券，只切换专用进程模式，两轮使用相反顺序测量。返回数据哈希一致，Redis 模式每次一次 GET，Caffeine 热读取不逐次访问 Redis。两轮平均吞吐约 3967、7355、17031 req/s。结果限于本机单热点条件；第一轮 Caffeine 有一次客户端 BindException，第二轮没有失败，原始样本都保留了。

PDF 的演变思路有助于解释 MySQL 查询/热点行锁、Redis 准入和异步落库的取舍；其中“数据编的就可以”、示例数字和生产 QPS 推断不适合作为自己的证据。

## 必须能解释的事实

1. 当前秒杀 HTTP 成功表示受理；Consumer 提交后才能说订单已创建，没有真实支付。
2. 当前入口仍查询两次 MySQL，销售时间在 Java 校验；Lua 校验库存和购券资格。
3. `RedisIdWorker` 是相对时间戳＋Redis 日计数，不是标准雪花算法。
4. 重复消息不能仅靠捕获主键异常。当前先识别已存在订单，再决定是否扣库存，库存与插入位于同一事务；用户券唯一约束另作保护。
5. Outbox 是 Redis Stream，不是 MySQL Outbox 表；不是 Redis/Kafka/MySQL 的分布式事务。单 Broker、单副本和持续重试有明确容灾/积压边界。
6. 250 ms SQL 轮询得到首次可见延迟上界，不是精确 commit 时间。
7. Caffeine 5 秒 refresh 会重新读 Redis，Redis TTL 30 分钟；不代表每 5 秒更新 MySQL 内容。当前页面仍使用 mysql 模式，库存展示的更新失效未完成验收。
8. 17k req/s 来自同机、单热点、50 线程、每轮 30 秒、两轮均值，不能扩大成生产最大容量或并发用户数量。

## 下一步怎样补强，而不是扩写简历

优先优化并重测 Outbox 发布瓶颈，恢复一个事务可靠且业务语义对齐的同步基准，再进行同条件同步/异步对照。其次补缓存更新失效、冷缓存/多热点/过期回源测试；限流先修 member 唯一性和真实用户维度再压测。

如果以后确实开发支付/关单或缓存补偿，需要完整状态竞争、幂等返库存、事务/确认边界与故障恢复证据后再加回简历。当前无需为了凑满七条保留缺失功能。
