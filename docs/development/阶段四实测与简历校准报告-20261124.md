## 7. 限流、缓存与推荐后续压测

真实限流入口 `GET /shop/of/type?typeId={独立类型ID}`，方法维度 5 秒 5 次。顺序发送 20 次，5 成功、15 拒绝。直接在独立 Redis 执行原 `limiter.lua`：100 次相同时间戳全部放行，ZCard=1；10 个不同毫秒时间戳时 5 放行/5 拒绝。根因是每次 `math.randomseed(now)` 后取相同首个随机数，ZADD member 重复。复现键已删除，未修原代码。

推荐顺序：

1. **继续秒杀受理/完成分离测量**：先明确订单完成延迟目标，优化或可配置 Outbox 批量/频率与发送方式后，在相同库存、日志、机器和阶梯重测。保持投递重试和事务后确认，不能以异步数量堆积交换一个好看的 HTTP QPS。
2. **修复并验收同步基准后再做同步/异步对比**：历史自调用事务问题、时段校验、ID 返回、唯一约束与隔离条件先对齐；使用独立目录/工作区，不切当前分支；需要同时报告 HTTP 与完成延迟。当前不写同步提升百分比。
3. **继续缓存对比**：本轮三模式结果最适合简历。后续增加冷缓存、多热点、TTL 到期、空列表与更新失效；把动态券库存与静态营销信息分开验证后才考虑页面切换。
4. **限流先修正确性再压测**：保证同毫秒请求 member 唯一、使用真实 UserHolder 身份、明确可信 IP 来源与实际应用接口，然后测试边界、多用户/多 IP 隔离以及秒杀限流策略。
