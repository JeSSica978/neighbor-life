## 5. 复位与清理策略

`reset -Execute` 要求先停止注入、排空、订单集合/库存核对成功，随后**只停止专属 loadtest 后端**。工具检查8082无监听、对应 group 无成员且 Empty、lag=0、outbox=0；不会终止任何进程。复位复制自有券到**新 voucherId**，MySQL新库存为S，Redis新key SETNX为S。旧券、订单、库存和幂等记录保留，旧券在 manifest 中退为 inactive。重启专属后端后使用输出的新券ID；不会复位共享ID序列。

这没有恢复旧券的库存数值，而是提供具有相同初始条件的新券。当前 Kafka 消息会长期保留，原券删订单后复位库存会使重放破坏幂等，因此**不提供原ID破坏性复位**。正式矩阵优先每次新run/new用户/new券；reset仅供受控功能重测，不将旧JTL直接覆盖或混入正式统计。

`cleanup -Execute` 同样先要求后端停止、group Empty、提交offset追平、outbox=0、所有自有券库存不变量成立；如果存在results.jtl，还按主键批量证明每个成功受理ID都在MySQL且归属正确。确认无外来券/订单/笔记/用户依赖，非自有十表指纹与准备时一致，然后：

1. 保存清理前检查和reservation key清单、DB_DELETE_INTENT。
2. 在一个MySQL事务中删除自有订单→秒杀券→券→店铺→分类→用户，逐项验证归属/影响行数。
3. 保存DB_CLEANED；只删除这些券的Redis stock/资格/reservation、自有店铺缓存、该用户的登录code/session。session SCAN后按hash中的用户ID过滤，未记录Token也不输出。
4. 再核对非自有指纹，保存CLEANED/COMPLETE。DB事务提交后文件更新中断可按journal恢复；模糊的部分准备不自动清理。

清理不删除Topic/Group，不重置offset，不删除ID序列，不清空Redis，不删除其他run数据；私有CSV/JTL保留为本地证据。**清理后的run不得再次启动消费者或重用其group**。已停止、已追平的旧group保持其offset，防止已清理订单对应消息再进入应用。

KafkaConfig 给新Topic设置 retention.ms/bytes=-1，独立Compose无法替代这个业务bean的Topic配置。本轮未改KafkaConfig或任何Topic。后续在证据保存、完全排空、停用该run后，可单独授权将其**专属测试Topic** retention.ms改为有限时长（如86400000），等待Kafka正常segment清理；记录生效参数和磁盘占用，保留group offset。不要删除当前默认Topic或reset offset。当前自动消息物理清理未实施，长期磁盘回收UNKNOWN。

## 8. 订单首次可见观察器与一致性

[LoadtestObserver](D:/Development/neighbor-life/tools/loadtest/observer/LoadtestObserver.java) 通过入口的observe动作运行，默认dry-run。实际采集优先用lt_observer（SELECT-only），每次查询autoCommit避免长事务读旧快照；不启动KafkaConsumer、不poll业务消息、不提交offset、不调用订单HTTP。

观察器可先于JMeter启动，等待同run `results.jtl` 出现；只读完整已换行的CSV行，不接纳截断/格式错误文件。提取成功受理orderId与userId，按主键IN最多500个一批查询，每轮目标250ms；只查询尚未首次可见的ID，记录实际轮询间隔/SQL往返。高积压时可能一轮多批，实际采样间隔会增加，不能认定误差恒等250ms。

`first-visible-*.csv` 记录请求start、HTTP接受end、JTL发现、SQL首次可见、用户/订单ID、实际poll gap、query耗时、observer是否晚启动。

```text
受理到首次可见延迟上界 = max(0, first_visible_ms - http_accept_ms)
请求开始到首次可见延迟上界 = max(0, first_visible_ms - http_start_ms)
JTL发现延迟 = max(0, jtl_discovered_ms - http_accept_ms)
```

此上界包含文件flush/发现、观察器启动滞后、线程调度、查询和轮询误差；订单也可能在HTTP返回前已经提交，此时受理后的实际等待为0。不能用订单ID时间或create_time冒充精确commit时刻。观察器需要在测量前启动、与JMeter在同机使用同一毫秒时钟；已完成订单晚启动造成的上界不参与公平延迟比较。精确commit延迟UNKNOWN。

`pipeline-*.jsonl` 每约1秒记录HTTP受理唯一ID数、已在SQL首次可见的完成数、尚不可见数、重复响应ID数、最大实际采样gap、Outbox XLEN/最早entry年龄，以及Kafka CURRENT-OFFSET/LOG-END-OFFSET/LAG和group state。完成TPS当前输出为观察窗口累计平均，稳态/排空分段TPS应从first-visible事件按timestamp重新分桶；它只统计JTL已知ID，不是全库订单扫描统计。

观察结束写observer-summary，包括缺失ID和最终consistency。初始250秒覆盖70秒注入+180秒排空，但启动/统计耗时会占用窗口，应按实际开始结束时间编排并在必要时重新只读检查。观察器负担、采样误差与实际运行效果UNKNOWN。

库存核对对每张manifest券统计MySQL stock、Redis stock、订单数、Redis资格用户集合、未完成reservation；排空后要求：

```text
Redis stock = MySQL stock = S - MySQL订单数 >= 0
MySQL订单数 = 唯一购买用户数 = Redis资格人数
Redis资格用户集合 = MySQL订单用户集合
unfinished reservations = 0
Outbox XLEN = 0，Kafka LAG = 0
每个成功受理ID在MySQL中归属正确且只有一条
```

检查不会写库存“修平”结果。reservation与资格集合扫描、按券统计只在初始/inspect/结束/清理核对时执行；250ms周期用订单主键批量查，不高频全表扫。排空不变量不适用于尚在处理的瞬间；pending应先等待或修复。本轮没有实际库存、orderId或lag采样，不能填假数据。
